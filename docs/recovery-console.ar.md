# مراقبة الصيانة والنسخ من لوحة المالك

**قسم الصيانة للمراقبة والقراءة فقط.** لا يُمنح حساب مالك التطبيق التحكم بعمليات
استعادة AWS أو نسخ الملفات أو حذف بيانات السوق. هذا القرار يحل محل تصميم أدوات
الاسترجاع التنفيذية الذي جُهز محليًا سابقًا ولم يُنشر.

## ما يبقى في القسم

- أعداد الإعلانات المحذوفة والصور المرتبطة والبلاغات المغلقة وبيانات البحث والطلبات.
- مستعرض الجداول الحالي، مع حجب الأسرار والرموز والروابط الخاصة، والبحث والترقيم.
- فحص توافق المخطط والترحيلات والعلاقات، دون تطبيق ترحيلات أو إصلاحات.
- عرض رسالة الموقع الحالية وحالتها؛ لا يوجد تحرير أو نشر أو حذف من القسم.
- حالة نسخ RDS ومدة الاحتفاظ واللقطات المتاحة، عند تجهيز صلاحية قراءة بياناتها.
- حالة نسخ الملفات إذا جُهز مصدر مستقل للقراءة فقط. عدم تجهيز الربط لا يعني عدم
  وجود نسخ خارج التطبيق، ولا يثبت توفر نسخة قابلة للاستعادة.
- تنزيل خطة طوارئ إرشادية لا تحتوي كلمات مرور أو أوامر تنفيذ من لوحة المالك.

الجلسة مقيّدة بالمالك، وتُمسح البيانات المعروضة عند تبديل الحساب أو سحب الصلاحية.
استعلامات فحص القاعدة وأعداد الصيانة تستخدم معاملات `READ ONLY` بمهل محدودة.

## العمليات المتقاعدة

أزيلت واجهات التنظيف المحدود والمسح الشامل والإقرارات والمعاينات الموقعة، وأزرار
إنشاء قاعدة مستعادة وفحصها ونسخ الملفات وإعادتها. أزيل أيضًا كود SQL للمسح الشامل
وكود الحذف في الصيانة، وWorker الاسترجاع غير المنشور وإعداداته.

مسارات `/api/admin/maintenance` و`/api/admin/recovery` و`/api/admin/site-message`
تُبقي `GET` للعرض. ترفض `POST/PUT/PATCH/DELETE` بعد التحقق من الصلاحية، دون قراءة
الحمولة أو تنفيذ عمليات قاعدة بيانات أو تخزين. وتُرفض معاينة `resource=market_reset`.
الاستجابات `403 maintenance_read_only` أو `403 recovery_read_only` متعمدة؛ ليست
خطأ في النشر. لا يمكن لأي متغير إعادة تفعيل الإجراءات، حتى لو بقي عميل قديم مفتوحًا.
المداخل البرمجية القديمة للمسح الشامل والتنظيف محايدة كذلك وتُرجع الرفض قبل الاتصال.

هذه القيود تخص قسم الصيانة؛ لا تغيّر وظائف العملاء المعتادة أو معالجة حذفهم
لإعلاناتهم وحساباتهم أو مهام دورة حياة الصور المرتبطة بتلك الوظائف.

## صلاحيات مراقبة AWS

استخدم **Instance role** بدور مراقبة محدود على App Runner. يقتصر القالب
[rds-instance-policy.example.json](../ops/recovery/rds-instance-policy.example.json)
على `DescribeDBInstances` و`DescribeDBSnapshots` و`DescribeDBInstanceAutomatedBackups`
في `eu-central-1`، ويتضمن منعًا لعمليات الإنشاء والاستعادة والتعديل والحذف ذات الصلة.
راجع جميع السياسات الملحقة بالدور؛ القالب المحلي ليس إثباتًا لحالة IAM الفعلية.

| المتغير | وظيفته |
| --- | --- |
| `SMARTSTORE_RECOVERY_MONITORING_ENABLED=1` | تفعيل قراءة حالة RDS فقط |
| `SMARTSTORE_RECOVERY_AWS_REGION` | المنطقة؛ الافتراضي `eu-central-1` |
| `SMARTSTORE_RECOVERY_ACCOUNT_ID` | حساب AWS الذي يملك القاعدة |
| `SMARTSTORE_RECOVERY_SOURCE_DB_IDENTIFIER` | المصدر؛ الافتراضي `smartstore-db` |

المراقبة الخارجية معطلة افتراضيًا حتى تُجهّز صلاحيات القراءة. المشروع يستخدم
`Configuration source = REPOSITORY`؛ تُضاف القيم غير السرية إلى `apprunner.yaml`
بعد التحقق منها. لا تحتاج مراقبة النسخ شهادة اتصال PostgreSQL أو كلمة مرور جديدة
أو مجموعات شبكة لاستعادة قاعدة أو أي صلاحيات إنشاء موارد.

مراقبة ملفات الصور اختيارية وغير مجهزة بهذا التغيير. إذا جُهّز لاحقًا مصدر حالة
مستقل، تُستخدم متغيرات `SMARTSTORE_RECOVERY_MEDIA_MONITORING_ENABLED/ORIGIN/SECRET`
وعنوان `https://recovery-status.souqhamad.com`. الاتصال الوحيد هو `GET /v1/status`.
يلزم اعتماد منفصل يسمح بالقراءة فقط؛ لا تستخدم أسرار Worker التحكم أو مفاتيح R2.
الأسماء القديمة `SMARTSTORE_RECOVERY_ENABLED` و`SMARTSTORE_RECOVERY_MEDIA_ENABLED`
واعتمادات التنفيذ القديمة لا تمنح أي إجراء أو صلاحية للمراقبة الجديدة.

## الاستعادة عند الحاجة

تنفذ من AWS بهوية تشغيل مستقلة محمية بـMFA وصلاحيات محددة، خارج جلسة التطبيق.
ابدأ بنسخة منفصلة من RDS قبل وقت الحادث، وافحص البيانات ثم راجع التحويل.
ملفات الصور والأدلة تحتاج نسخًا مستقلة؛ RDS يحفظ مراجعها ولا يحفظ محتواها.
إذا تقرر حفظ نسخ الملفات في S3، يُجهّز ذلك في AWS خارج لوحة التطبيق ويُختبر بصورة
مستقلة. هذا التغيير لم ينشئ حاوية S3 أو يفعّل نسخ ملفات جديدة.

احتفظ بخطة الطوارئ خارج التطبيق حتى تكون متاحة عند تعطل قاعدة البيانات أو الدخول.
راجع الحذف المشروع للحسابات والأدلة والتغييرات اللاحقة لنقطة الاستعادة قبل إعادة
بيانات قديمة، ولا تعتبر ظهور Snapshot أو نجاح اختبار محلي إثبات استعادة إنتاج.

## التحقق

اختبارات Node وHTTP والمتصفح تتحقق من القراءة ورفض طلبات العملاء القديمة، ومن
عدم استدعاء معاملات حذف أو عمليات سحابية عند محاولة التنفيذ حتى مع الأعلام القديمة.
اختبار PostgreSQL المخصص يقارن بصمات الجداول قبل المحاولة وبعدها بقراءة فقط؛
لا ينشئ أو يحذف قاعدة أو بيانات. اختبارات RDS تستخدم مزودًا وهميًا؛ تجهيز IAM
ومشاهدة حالة النسخ الفعلية على AWS تبقى خطوة مستقلة.

مرجع: [أقل الصلاحيات وMFA في AWS](https://docs.aws.amazon.com/IAM/latest/UserGuide/best-practices.html).
