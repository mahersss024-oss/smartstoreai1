# الاسترجاع من لوحة المالك

القسم الجديد داخل **لوحة المالك ← الصيانة والتنظيف ← النسخ والاسترجاع**.
تقتصر واجهته وAPI على حساب المالك المضبوط في إعدادات السيرفر؛ صلاحية المدير العادي لا تكفي.
لا يغير وظائف التطبيق أو مساراته، ولا يحتاج إصدار جوال جديد أو ترحيل قاعدة بيانات.

## ما يفعله الكود

| العملية | التنفيذ |
| --- | --- |
| قراءة الجاهزية | قراءة RDS وWorker عند الضغط على تحديث، مع تمييز غير مجهز/متعذر/متاح |
| استعادة قاعدة | اختيار لقطة متاحة أو وقت محدد داخل نافذة PITR، ومعاينة موقعة تنتهي بعد عشر دقائق |
| تنفيذ الاستعادة | إنشاء مثيل خاص جديد باسم عشوائي `souqhamad-recovery-*`؛ تأكيد العبارة والسبب والتكلفة مطلوب |
| فحص القاعدة | اتصال مستقل عبر TLS موثق، ومعاملة للقراءة فقط: ترحيلات وبصماتها، مخطط وعلاقات وأعداد ومهام مؤجلة |
| نسخ الملفات | مهمة Queue مستقلة، بصفحات من 25 ملفًا؛ تشمل الصور الدائمة وصور الحسابات والأدلة ونسخ WebP المرحلية |
| التحقق من الملفات | حساب SHA256 للمحتوى وقراءته مجددًا من الخزنة، مع سجل صفحات مترابط وموقع |
| استعادة الملفات | قراءة النسخة المكتملة والتحقق منها ونسخها إلى `quarantine/` داخل الخزنة الخاصة |
| خطة الطوارئ | تنزيل JSON بلا كلمات مرور أو مفاتيح، للاحتفاظ به خارج السيرفر |

لا يوجد زر SQL حر، ولا استبدال لقاعدة الإنتاج، ولا نسخ ملفات فوق الحاويات الحية.
تتحقق الاستعادة من هوية المصدر والهدف وتوقيع العملية، ولا تعتمد على تشابه الاسم.
تبقى عمليات الحذف والتعديل والكتابة في التطبيق كما هي.

## الحالة عند تسليم الكود

أعلام الإنشاء والنسخ الجديدة معطلة افتراضيًا. لم ينشئ هذا التغيير مثيل RDS أو حاوية
أو طابورًا على الحساب الحي. نجاح الاختبارات المحلية ليس إثباتًا لاستعادة إنتاج فعلية.
النسخ التلقائي الحالي لـRDS مستقل عن هذه الأعلام؛ أكّد المالك احتفاظه بسبعة أيام.
اللقطة اليدوية `souqhamad-prelaunch-20261103` ظهرت Available في صورة المالك.

تغطي RDS سجلات قاعدة البيانات، ولا تتضمن ملفات R2. لا يمكن استعادة ملف حُذف من
Cloudflare قبل وجود نسخة مستقلة منه. لا يجري هذا الكود مسحًا شاملًا أو حذفًا للنسخ.

## تجهيز AWS مرة واحدة

1. من RDS تأكد من استمرار النسخ الآلي ونافذة PITR، واحتفظ بلقطة قبل أعمال التنظيف.
2. اختر DB subnet group خاصًا وSecurity Groups لنسخ الاستعادة. اسمح بمنفذ 5432
   من مجموعة اتصال App Runner فقط؛ لا تفتح قاعدة البيانات للإنترنت.
3. أضف صلاحيات الاستعادة إلى **Instance role** للتطبيق، وليس دور سحب المصدر أو
   GitHub. راجع القالب [rds-instance-policy.example.json](../ops/recovery/rds-instance-policy.example.json).
   استبدل اسم subnet group، وتحقق من parameter/option groups الفعلية قبل استخدامه.
   القالب ليس إثباتًا لصلاحيات IAM الحية؛ اختبره بـIAM Policy Simulator ثم تجربة منفصلة.
   وصول snapshot في القالب محصور بالحساب والمنطقة، والكود يتحقق أنه لنفس المصدر
   `DbiResourceId`. يمكن تضييق القالب إلى ARNs اللقطات المعتمدة.
4. لا تضف `AdministratorAccess` أو `rds:*`. لا يحتاج هذا الكود حذف أو تعديل الإنتاج
   أو تعديل `DATABASE_URL` عبر AWS API. إن كانت النسخة مشفرة بمفتاح KMS مخصص،
   راجع سياسة ذلك المفتاح وصلاحية إنشاء grant لخدمة RDS بصورة منفصلة؛ القالب لا يمنح KMS.
5. ثبت حزمة شهادات RDS الرسمية في ملف داخل نسخة السيرفر المنشورة، وحدد مساره
   **المطلق** في `SMARTSTORE_RECOVERY_CA_BUNDLE_FILE`. يجب أن يبقى الملف متاحًا
   بعد البناء، وليس على جهاز المطور فقط. لا يحمّل API شهادة من عنوان يرسله المتصفح.
   المصدر: [شهادات RDS الرسمية](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/UsingWithRDS.SSL.html).
6. أدخل القيم التالية في مصدر إعدادات التشغيل المعتمد. المشروع يستخدم
   `Configuration source = REPOSITORY`؛ لذلك عدّل `apprunner.yaml` بعد معرفة القيم
   الفعلية، وأضف مرجع Secrets Manager لسر Worker. إضافة أسماء إلى ملف `.env.example`
   لا تضبط خدمة AWS. حافظ على `AUTH_SECRET` الحالي، ولا تضع مفاتيح AWS دائمة في الكود.

| المتغير | القيمة |
| --- | --- |
| `SMARTSTORE_RECOVERY_AWS_REGION` | `eu-central-1` |
| `SMARTSTORE_RECOVERY_ACCOUNT_ID` | حساب AWS الذي يملك القاعدة |
| `SMARTSTORE_RECOVERY_SOURCE_DB_IDENTIFIER` | `smartstore-db` |
| `SMARTSTORE_RECOVERY_SECURITY_GROUP_IDS` | معرفات مجموعات النسخة الخاصة، مفصولة بفاصلة |
| `SMARTSTORE_RECOVERY_DB_SUBNET_GROUP` | اسم مجموعة الشبكات الخاصة |
| `SMARTSTORE_RECOVERY_DB_INSTANCE_CLASS` | اختياري؛ الافتراضي فئة المصدر |
| `SMARTSTORE_RECOVERY_CA_BUNDLE_FILE` | مسار PEM الموثق داخل السيرفر |
| `SMARTSTORE_RECOVERY_ENABLED` | `0` أثناء التجهيز؛ `1` يسمح بإنشاء نسخ برسوم AWS |

إنشاء نسخة منفصلة له تكلفة مستمرة حتى حذفها من AWS، وحماية الحذف مفعلة عليها.
تنظيف المثيل التجريبي بعد اعتماده إجراء مشغل من AWS؛ اللوحة لا تمنح صلاحية حذفه.
الواجهة تعرض مجموعة محدودة من اللقطات والمثيلات؛ استخدم AWS للفهرس الكامل.

## تجهيز Cloudflare مرة واحدة

هذه موارد استرجاع جديدة، مستقلة عن `souqhamad-image-pipeline` وعن مسار رفع الصور.

1. أنشئ حاوية خاصة `souqhamad-recovery-vault`. أبقِ Public Development URL والدومين
   العام للحاوية معطلين. لا تضفها إلى صلاحيات مفاتيح التطبيق التي تحذف الصور الحية.
2. أنشئ طابوري `souqhamad-recovery-jobs` و`souqhamad-recovery-jobs-dlq`.
3. راجع [wrangler.jsonc](../cloudflare/recovery/wrangler.jsonc). أسماء المصادر:
   `souq-hamad-listings` و`souqhamad-evidence` و`souqhamad-image-intake`.
   الربط R2 binding نفسه ليس صلاحية قراءة فقط؛ الكود يستخدم `list/get` للمصادر.
   قيّد صلاحية تعديل Worker والوصول للخزنة على فريق التشغيل.
4. أنشئ سرًا جديدًا مستقلًا للاسترجاع، بطول 32 حرفًا على الأقل. ضعه باسم
   `RECOVERY_WORKER_SECRET` في Worker، وبنفس القيمة باسم
   `SMARTSTORE_RECOVERY_MEDIA_SECRET` في Secrets Manager. لا تستخدم سر معالجة الصور.
   احتفظ بنسخة آمنة منه: توقيعات manifest القديمة تحتاج مفتاحها؛ تغييره بلا خطة
   انتقال مفاتيح يجعل النسخ القديمة غير قابلة للتحقق بهذا الإصدار.
5. انشر Worker من جذر المشروع بعد إنشاء الموارد:

   ```powershell
   pnpm.cmd dlx wrangler@4.154.0 secret put RECOVERY_WORKER_SECRET --config cloudflare/recovery/wrangler.jsonc
   pnpm.cmd dlx wrangler@4.154.0 deploy --config cloudflare/recovery/wrangler.jsonc
   ```

6. اربط Custom Domain مستقلًا `recovery.souqhamad.com`. ملف الإعداد لا يضيف route
   إلى صور العملاء ولا يغير DNS للموقع. لا تعرض الحاوية نفسها عبر هذا الدومين.
   يبقى API محميًا بتوقيع HMAC يتضمن الوقت والطريقة والمسار وبصمة جسم الطلب.
7. فعّل `RECOVERY_MEDIA_ENABLED="1"` في إعداد Worker بعد التجهيز، ثم انشر النسخة
   المطابقة. إذا غيرت القيمة من اللوحة فحدّث ملف النشر كذلك كي لا يعيد النشر تعطيلها.
8. في إعداد تشغيل السيرفر أضف `SMARTSTORE_RECOVERY_MEDIA_ORIGIN=https://recovery.souqhamad.com`
   والمرجع السري، ثم `SMARTSTORE_RECOVERY_MEDIA_ENABLED=1`. حدّث اللوحة وتأكد أن
   الجهتين تسمحان بالنسخ. لا تصل مفاتيح R2 أو السر إلى المتصفح.
9. أنشئ نسخة من لوحة المالك، وانتظر **completed**، ثم اختبر الاستعادة إلى العزل.
   راقب الطابور وDLQ وسجلات `recovery_job_retry`؛ وجود نسخة queued لا يثبت اكتمالها.

النسخ الحالية بطلب المالك. مهمة Cron تصلح إرسال المهام المعلقة فقط، ولا تنشئ نسخة
يومية جديدة تلقائيًا. حدد جدول النسخ ومدة الاحتفاظ وموافقات إتلاف الأدلة قبل تفعيل
جدولة دائمة؛ لا توجد سياسة حذف آلي أو قفل احتفاظ دائم مفروضان على بيانات العملاء.
تنقل العملية نسخ التسليم المحفوظة كما هي، ولا تولد أو تعيد الاحتفاظ بالصور الخام
في `intake/v1/`. تشمل JPEG/PNG القديمة الدائمة إذا كانت هي ملفات العرض الفعلية.

## تمرين الاستعادة قبل الاعتماد

1. سجل وقت البداية والنسخة التي ستستعيدها. اختر PITR قبل حادث الاختبار أو لقطة محددة.
2. من حساب المالك حدّث الحالة، واطلب المعاينة، ثم اقرأ اسم المصدر والهدف وتكلفة النسخة.
3. اكتب السبب والعبارة المعروضة واقبل التكلفة، ثم نفذ مرة واحدة. عند انقطاع الرد حدّث
   الحالة قبل أي طلب جديد؛ قد تكون AWS بدأت الإنشاء بالفعل.
4. بعد `available` افحص القاعدة المنفصلة. يجب نجاح TLS والقراءة فقط والمخطط
   والترحيلات والعلاقات؛ التقرير يعرض أعدادًا ولا يعرض سجلات العملاء أو كلمات المرور.
   قد تحتاج قواعد كبيرة مدة أخرى للفحص؛ انتهاء مهلة الفحص ليس دليل فقد بيانات.
5. اختر نسخة ملفات مكتملة واستعدها إلى العزل. طابق مراجع الصور من قاعدة الاستعادة
   مع manifest والتحقق من SHA256، بما يشمل الأدلة وصور الحسابات.
6. اختبر نسخة التطبيق على بيئة معزولة متصلة بالنسخة المستعادة عند الحاجة؛ لا توجه
   تطبيقات العملاء إليها أثناء التمرين، ولا تشغّل إشعاراتها أو مهام تنظيفها.
7. سجل مدة الاستعادة، وأحدث بيانات مؤكدة، والفجوة المفقودة، ونتيجة مطابقة الملفات.
   أزل موارد التمرين من AWS بعد المراجعة. لا تسجل كلمة المرور في تقرير التمرين.

فحص القاعدة والملفات منفصل حاليًا؛ لا توجد مطابقة تلقائية شاملة بين كل رابط صورة
في قاعدة مستعادة وmanifest. النسخة الممسوحة من R2 متحققة **لكل ملف أثناء نسخه**،
وليست لقطة ذرية في نفس لحظة PITR لقاعدة البيانات.

## عند حذف بيانات الإنتاج فعليًا

1. سجل وقت الحادث وسببه. أوقف مصدر الكتابة والتنظيف قبل التحويل. رسالة الموقع
   وحدها لا توقف العمليات. عند تعذر ضمان ذلك استخدم Pause للخدمة من AWS، وتعامل
   مع مهام Cloudflare والطلبات المعلقة؛ حينها لن تعمل لوحة تعتمد على تلك الخدمة.
2. استعد إلى قاعدة خاصة جديدة من **وقت قبل الحذف**، داخل نافذة RDS الفعلية.
   لا تستخدم أحدث وقت تلقائيًا؛ فقد يكون بعد وقوع الحادث.
3. احتفظ بالقاعدة الحالية للفحص ومصالحة التغييرات السليمة التي حدثت بعد نقطة الاستعادة.
4. افحص النسخة المعزولة واستعد الملفات إلى العزل. راجع الحسابات المحذوفة/المعطلة
   والأدلة المتلفة بصورة مشروعة والمهام القديمة قبل إعادتها.
5. **لا يوجد حاليًا سجل مستقل كامل لقرارات الحذف خارج قاعدة الإنتاج.** لذلك لا يسمح
   هذا التنفيذ بتحويل آلي إلى نسخة قديمة أو إعادة جميع ملفات الأدلة عمياء.
   نجاح الفحص التقني لا يلغي مراجعة صلاحية إعادة البيانات وحقوق أصحابها.
6. بعد اعتماد المشغل، انسخ الملفات المسموح بإعادتها فقط إلى مفاتيحها الصحيحة، وطابق
   مراجعها مع القاعدة، وحدّث سر `DATABASE_URL` يدويًا إلى المثيل المتحقق منه ثم أعد
   نشر الخدمة. أبقِ الأسرار الأخرى الصحيحة وراجع مهام التنظيف والإشعارات قبل تشغيلها.
   حدّث `SMARTSTORE_RECOVERY_SOURCE_DB_IDENTIFIER` وسياسة IAM لتتبّع المصدر الجديد،
   وتحقق من نسخ RDS الآلية واحتفاظها على المثيل الجديد؛ لا تفترض انتقال إعداد السبعة
   أيام تلقائيًا. نزّل خطة طوارئ محدثة بعد التحويل.
7. افحص `/api/health` ومسار العميل والصور والمحادثات، ثم افتح الكتابات تدريجيًا
   وسجل ما لم يُسترجع وسبب الفقد. لا تعد بتعافٍ بلا فقد أو وقت ثابت قبل تمرين حي.

احفظ هذا الدليل وخطة الطوارئ خارج App Runner. إذا حُذفت حسابات الدخول أو تعطلت
القاعدة، تكون الاستعادة عبر حساب AWS/Cloudflare المخوّل؛ لا نضيف تجاوزًا للمصادقة.

## حدود الاختبارات

اختبارات RDS تستخدم مزود AWS وهميًا للتحقق من العقود والصلاحيات والتزامن، واختبارات
فحص القاعدة تستخدم جلسة محاكاة للتحقق من الاستعلامات المقيدة. اختبارات Worker تنسخ
بايتات حقيقية في R2/Queue محليين وهميين، وتشمل الفشل والتكرار والتلف. اختبارات المتصفح
تختبر واجهة المالك باستجابات سحابية محاكية. هذه لا تثبت IAM أو الشبكة أو RDS الحي.
أمر `scripts/dev-tools/postgres-restore-check.mjs` الموجود سابقًا تمرين PostgreSQL
محلي مستقل؛ ليس إثبات استعادة لقطة AWS. الاعتماد الإنتاجي يتطلب التمرين أعلاه.

مراجع: [RDS PITR](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_PIT.html)،
[صلاحيات RDS](https://docs.aws.amazon.com/service-authorization/latest/reference/list_rds.html)،
[R2 bindings](https://developers.cloudflare.com/r2/api/workers/workers-api-reference/).
